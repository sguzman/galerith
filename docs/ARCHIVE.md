# 🗃️ Native download archive (preview)

The `--download-archive FILE` option creates a SQLite file and records **only successfully completed downloads**. Previously recorded items are skipped before fetching their media bytes. Existing files skipped by filename alone are **not** automatically recorded, since their origin has not been verified.

## Format

- Database: SQLite table `downloads(category, identity, recorded_at)`; unique composite key on category and identity
- For direct-media URLs, `identity` is the SHA-256 digest of the URL and `category` identifies the extractor. Signed URLs are not stored in plaintext.
- For general items with a post ID, `identity` is `post:POST_ID:url-sha256:DIGEST`, scoped to the extractor. This preserves multiple originals under one post: query-distinguished URLs have different fingerprints but their credentials are never stored in plaintext.
- For pinned **Piczel** user galleries and individual-image pages, upstream `archive_fmt = "{id}_{num}"` uses a zero-based original position. The native adapter derives `id` from the API-backed post ID and canonical `piczel_ID_title_NN.ext` filename, validates the official source URL, first-party original media origin and extension, and writes only a SHA-256-based native identity. Each position remains distinct even for identical post IDs or original URLs. Default and explicitly `piczel`-prefixed SQLite entries migrate idempotently; malformed, ambiguous and custom-prefix rows are not treated as completed downloads. Pinned Piczel **folder** mode instead uses `f{folder[id]}_{id}_{num}`. Galerith's current `MediaItem` does not retain independently verifiable per-post folder ownership, so folder-source archive lookups and folder-key migration fail closed rather than substituting the user/image key. This deliberately excludes complete folder parity.
- For pinned **Slideshare** public presentations, gallery-dl archives each image by `{presentation}_{num}`, so separate pages of the same deck must never suppress each other. The bounded native adapter verifies the canonical source presentation slug and numbered `slug-NN.jpg` filename against the official `slidesharecdn.com` slide-image URL and its `/95/...-NUM-1024.jpg` page marker. A changed CDN host, display title or presenter does not change the pinned slug/page identity; different deck slugs or positions remain separate. Default and matching explicitly `slideshare`-prefixed foreign SQLite keys import privately, idempotently and offline, rejecting malformed/padded numbers, unsafe hosts and ambiguous named tables. This covers native public Next.js preview slides only, not arbitrary upstream presentation options or templates.
- For pinned **Catbox**, the direct-file extractor archives `{filename}` (original basename without extension), while album mode archives `{album_id}_{filename}`. Source-scoped native records distinguish a direct `files.catbox.moe/abc123.jpg` from that same file encountered inside two different public `/c/ALBUM` pages, and keep separate album originals distinct. To avoid confusing a direct filename containing underscores with an album key, the bounded migration adapter accepts only unambiguous alphanumeric/hyphen file stems and single-component album IDs. It verifies canonical first-party file URLs, the exact native basename and safe public album origin; imported keys are private hashed, read-only, idempotent and usable without the foreign SQLite file. Noncanonical names and arbitrary gallery-dl archive templates remain unsupported.
- For pinned **Webmshare** public video pages, upstream `archive_fmt="{id}"` uses the original case-sensitive video ID, not the display title, numeric parse or CDN location. The bounded native adapter matches canonical `ID.webm` or `ID title.webm` filenames against the exact official HTTPS video source and trusted Webmshare media hosts, retaining alphanumeric/underscore source IDs. Video title and CDN changes can reuse one hashed native identity. Default `webmshare{id}` and matching explicitly prefixed named SQLite rows migrate privately, idempotently and offline, while unsafe origins, mismatched filenames and arbitrary archive templates fail closed. Media URLs must end in WebM and may carry first-party signed query parameters. This is source-verified video-mode support, not complete upstream Webmshare metadata parity.
- For pinned **Lensdump** public single-image pages, upstream uses `archive_fmt="{id}"`. Its album extractor instead inherits `archive_fmt="{gallery_id}_{num}"` from `GalleryExtractor`; the native image adapter therefore accepts only a validated alphanumeric ID (no underscores) from the exact `https://lensdump.com/i/ID` page, matching the first-party CDN basename and canonical `lensdump_ID_original.ext` output. This conservatively rejects image IDs with underscores because they could be confused with an unrelated album-position archive entry. Source-verified image keys and category-prefixed SQLite imports are hashed, idempotent and offline-usable, with separate images never conflated; album mode remains URL-scoped and album keys are excluded from import. This is bounded image-mode migration, not general Lensdump gallery or arbitrary-template parity.
- For pinned **Listal** public individual images, upstream `archive_fmt = "{id}/{filename}"` identifies both the numeric picture ID and each original media basename, **excluding** its extension. Galerith derives those parts from the canonical `ID_original.ext` filename already produced by its source parser and verifies the individual-image URL plus official Listal/Lisimg media URL (including the actual basename). Distinct originals sharing a picture ID therefore never falsely skip each other. Default `listal{id}/{filename}` and exactly `listal`-prefixed named SQLite identities import idempotently, privately and read-only; a removed reference database is not needed for later skips. Noncanonical IDs, fake hosts, mismatched filenames and ambiguous people-listing context fail closed. Alternate filename formats, private listings and general gallery-dl archive migration remain unverified.
- For pinned **Pixeldrain** public file and album extractors, gallery-dl archives each downloaded file by `{id}`, independent of the album or original display name. The bounded native adapter obtains the exact file ID from its official `/api/file/{id}?download` media URL and verifies a matching public direct-file source or a public album/list origin. This permits the same file to be recognized across different albums and renamed output files, without storing the name or ID in plaintext. Default `pixeldrain{id}` and matching explicitly `pixeldrain`-prefixed named SQLite imports are idempotent and read-only. **Folder mode differs:** upstream archive format is `{path}_{num}`; native filesystem previews currently lack a complete, independently verified folder position, so folder-source archive migration and stable-ID matching fail closed. Album ZIP and arbitrary custom templates remain outside this verified adapter.
- For pinned **Lexica** public image search, upstream `archive_fmt = "{id}"` identifies the individual image, not its search query. The existing native extractor already provides the API image ID as both `id.jpg` and a first-party `/full_jpg/id` media URL; the bounded adapter verifies both, plus the official `https://lexica.art/?q=...` search origin. The same image can be recognized across different search phrases while unrelated images remain distinct, with only SHA-256 identities stored in native SQLite. Default `lexica{id}` and exact `lexica`-prefixed named-table entries migrate idempotently without modifying the source file and remain usable offline. Untrusted hosts, mismatched IDs and malformed queries are rejected. Other extractors, authenticated APIs, and arbitrary custom formats remain out of scope.
- For all pinned public **Unsplash** extractor families (individual photos, user photos/likes, collections and search), upstream `archive_fmt = "{id}"` identifies the underlying photo, not the page, search or signed CDN URL. The bounded native adapter uses the alphanumeric API photo ID already retained as the canonical `id.jpg` filename, verified against the official Unsplash source family and Unsplash CDN domains. A photo can be recognized across public collections, users and searches without storing its ID or query tokens in plaintext. Default `unsplash{id}` and exactly `unsplash`-prefixed SQLite entries migrate idempotently, preserve the source database and work after source removal. Unsupported, ambiguous, malformed or untrusted source URLs fail closed. This does not establish complete metadata, private album, API-authentication or arbitrary archive-template parity.
- For the pinned **35photo** individual-photo image extractor, gallery-dl uses `archive_fmt = "{id}_{num}"`. Galerith's bounded adapter trusts only the verified public `/photo_ID` source, official HTTPS 35photo CDN, numeric source ID and canonical `ID_NN.ext` filename emitted by the public image/series API. Distinct series originals are tracked separately by one-based position even when media URLs change. Native identities and imported archive keys are SHA-256-hashed, and default `35photo{id}_{num}` and exactly `35photo`-prefixed named SQLite entries migrate privately and idempotently with offline reuse. The pinned tag and genre formats are **different**, respectively `t{search_tag}_{id}_{num}` and `g{genre_id}_{id}_{num}`, and therefore are not imported as generic photo keys. Arbitrary listing-context, custom-template, non-image and authenticated cases remain unverified.
- For the pinned **Foriio** public work extractor, upstream `archive_fmt = "{work_id}/{file_id}/{num}"` distinguishes multiple originals within one work, including the same file ID appearing in another position. The bounded native adapter derives the work ID from its source post ID, file ID and position from its canonical `NN file-id.ext` filename, and checks the exact public work URL plus the original `foriio.imgix.net/store/` media host. Rotated original CDN filenames with the same trusted asset extension can share one hashed archive identity; unrelated work IDs, file IDs and positions never collide. Default `foriio{work_id}/{file_id}/{num}` keys and matching explicitly prefixed named-table entries migrate privately and idempotently. Ambiguous file identities, malformed positions, foreign sources and unsafe media origins fail closed. This covers the existing public image/copy-writing subset, not video, audio, arbitrary templates or complete Foriio parity.
- For the pinned **Lightroom** public shared-gallery extractor, upstream `archive_fmt = "{id}"` identifies individual Adobe assets rather than an album, display index, or CDN rendition. Galerith's bounded native adapter derives this ID only from the canonical `NNNN_asset-id.ext` filename produced by its own Adobe asset-list extractor, verified against the exact HTTPS Lightroom share origin and Adobe-family media hosts. A different rendition, index or shared album of the same asset can reuse its hashed native identity without revealing asset IDs or signed URLs in SQLite, while distinct assets remain separate. The canonical default `lightroom{id}` and exact `lightroom`-prefixed named-table rows can be imported idempotently, but unscoped named tables, malformed IDs, invalid hosts and noncanonical filenames are rejected. This does not establish complete gallery-dl Lightroom or authenticated-share parity.
- For pinned **Fapello** public posts, the upstream archive format is `{type}_{model}_{id}`. The existing native single-media preview supports stable source-verified photo/video identities only when trusted original media extensions unambiguously determine the type. Native identity hashes the type/model/post key without storing model names, and separates photo and video variants and different models with identical numeric IDs. Canonical default keys and exact `fapello`-prefixed custom SQLite rows may be migrated idempotently; ambiguous custom tables and malformed entries are rejected. This does not establish arbitrary Fapello metadata or archive-template parity.
- For pinned **Fapachi** public post URLs, the upstream format is `{user}_{id}`, and the default key is `fapachi{user}_{id}`. Native source-verified keys hash the user-and-post identity rather than storing the username in plaintext; unlike ID-only archives, two users with overlapping post IDs or identical media URLs do not suppress one another. Exact official post origins, canonical positive IDs, source-matched media and first-party HTTPS images are required. Hash-only idempotent imports from default archives and category-prefixed named tables are supported, while unprefixed/ambiguous keys, malformed IDs and feed pages are rejected. This covers only the existing bounded public-post extractor, not every Fapachi upstream mode.
- For the pinned **PhotoVogue** photographer feed, the upstream archive format is `{id}` and the default archive entry is `photovogue{id}`, independent of photographer. Native `image-id:ID` records require a validated PhotoVogue photographer source and a trusted Vogue HTTPS media origin. Distinct photo IDs never collide, while the same photo from different photographer feeds remains one archive identity. Read-only default-table imports and explicit `photovogue`-prefixed custom table imports are canonical and hashed. Unprefixed numeric named-table entries and leading-zero entries are excluded. This covers the existing public photographer-feed preview only.
- For the pinned **500px** single-photo extractor, the upstream archive format is `{id}` and the default archive key is `500px{id}`. Native `image-id:ID` records require a source-verified individual 500px photo and a trusted 500px-family HTTPS media host. These survive CDN/rendition and signed URL changes without confusing different photo IDs. The default upstream archive table and explicitly category-prefixed named tables can be imported privately using hashes; unsupported, ambiguous, malformed or leading-zero IDs are not accepted. The offline migration and pinned oracle tests cover this **bounded single-photo subset**, not user galleries or general 500px archive parity.
- The pinned Philomena sites (Derpibooru, Ponybooru, Furbooru) have a narrower, single-image-ID contract. New native records use `identity = image-id:ID`, scoped to the site category, so rotating signed URLs and CDN hosts no longer create duplicate downloads. Old Galerith `post:ID:url-sha256:DIGEST` rows are still recognized for the exact original URL. On a successful match, Galerith atomically adds the stable native ID without deleting the legacy record or downloading again; future CDN/token rotations then match. If the *first* revisit already uses a rotated URL, that old digest cannot prove identity, so one safe re-download may occur.
- Legacy `post:POST_ID` rows cannot distinguish which original was previously downloaded. They remain in the database but do not suppress media under the new key. This may cause safe repeat downloads after upgrading; it avoids silently dropping images.
- For source classes outside the verified scopes listed below, signed URL rotations can change a native URL-digest identity and cause a safe repeat download. The supported upstream `archive(entry TEXT PRIMARY KEY)` keys include **directlink**, **Philomena** (Derpibooru/Ponybooru/Furbooru), **500px single photos**, and the narrowly verified Danbooru/e621-family post, pool, favorite, tag, media-asset and dated-popular formats documented below. Foreign lookup is read-only. Unlisted classes, arbitrary templates, authenticated identity assumptions and general migration remain unsupported.
- **Cross-extractor import safety:** Bare numeric `4chan` rows are not valid gallery-dl archive identities: its pinned key includes board, thread and media `tim`. Named SQLite tables with a custom prefix do not prove directlink provenance merely because a row resembles `domain/path/file.ext`; only an empty prefix (upstream's named-table default) or the explicit `directlink` prefix is recognized for directlink imports and live read-only skips. Other custom prefixes are deliberately unsupported for directlink to avoid confusing another extractor's rows with completed downloads. The same rule is enforced on in-process reference lookups, imported rows, and native archive reopen; ambiguous input is ignored rather than falsely suppressing a download. This remains a bounded compatibility subset.
- To migrate supported archive keys offline, run `galerith --download-archive NATIVE.sqlite --gallery-dl-archive ORIGINAL.sqlite --archive-import` (no URLs). The importer scans the foreign archive, hashes supported keys into an `imported_gallery_dl(category, archive_sha256)` table in a single native SQLite transaction, and prints recognized/new counts. It is safe to rerun, does not persist plaintext filenames/source URLs, and leaves the original unchanged. After importing, downloads can consult the native file *without* supplying `--gallery-dl-archive`. This supports only the pinned default or explicitly prefixed class-specific archive entries described below; unsupported or ambiguous rows are ignored, not counted as imported. This is a **partial** migration, not general gallery-dl interchange.
- For live read-only lookup of a separate, existing gallery-dl SQLite file, pass `--download-archive NATIVE.sqlite --gallery-dl-archive ORIGINAL.sqlite`. The optional `--gallery-dl-archive-table TABLE` selects a named foreign archive table for both live lookups and offline imports; the default is `archive`. **Pinned upstream behavior:** the implicit default table uses the extractor's category as the archive prefix, but explicitly selecting a table defaults to an *empty* prefix. `--gallery-dl-archive-prefix PREFIX` overrides that setting (including the empty string). For an empty or unrelated prefix, bare numeric Philomena IDs are ambiguous across sites: Galerith refuses to import or suppress them; a matching explicit site prefix such as `derpibooru` is required. Supported directlink keys are normalized to category-scoped, hashed native IDs so imported records survive disconnecting the source archive. Table names are strictly quoted and validated for an `entry TEXT PRIMARY KEY` column, so punctuation and spaces do not become executable SQL. The reference is opened with SQLite read-only flags and checked for an `archive(entry TEXT PRIMARY KEY)` table before the native file is created. Only the verified classes documented below are consulted; arbitrary extractor archive formats are not guessed. All completed downloads are recorded exclusively in Galerith's native database. Missing or invalid references are rejected. Equal paths, symlink aliases and (on Unix) hard-link aliases are rejected before Galerith can write to the source file.
- Reopening the database retains results across invocations.
- Cooperating Galerith processes serialize the archive check, download, and record with OS advisory locks. The 64 stable lock stripes live next to the canonical database path in a `.galerith-locks` directory; relative and symlink database aliases share locks. Guard release on process exit/crash permits recovery without a stale claim. Lock files are never unlinked and contain no media URLs.
- Extract-only/dry-run modes (`--get-urls`, `--dump-json`, `--simulate`, `--no-download`) do not open or modify the archive.
- A successful HTTP status is not enough to archive a zero-byte media response: empty `200` and `204` bodies fail without a completed output file, and an existing zero-byte output is not treated as a valid filename skip (including with `--archive-event skip`). A resumed `206` without `Content-Range` invalidates the stale partial and sidecar; retries can then restart from byte zero. An unsolicited `206` response when no range was requested is likewise rejected and cleared, with an optional fresh full-download retry. A validated partial survives rate limits, while weak ETags without a strong alternative are not used in `If-Range` requests. These behavior limits are covered by localhost CLI/download regression tests; generic content-integrity checksums are not provided.
- **Encoded HTTP media safety:** Galerith explicitly requests `Accept-Encoding: identity` for media GETs because stored resume offsets are byte positions in the original representation. If a server nonetheless returns `Content-Encoding` other than `identity`, both fresh `200` and resumed `206` responses fail closed: their partial bytes and sidecar are cleared, no successful archive entry is recorded, and a later unencoded transfer can succeed. This is a conservative resumable-download subset, not full transparent content-decoding parity.
- **Misleading binary response bodies:** Some hosts omit `Content-Type` or disguise a block page as `application/octet-stream`. For established binary/media, PDF and archive extensions, Galerith also samples at most the first 160 response bytes for recognizable HTML document openings or JSON error keys. A detected block page invalidates the partial/sidecar and cannot create a successful archive entry; a later valid response is still downloadable. Real `.html` and `.json` downloader-library outputs are not subject to this binary-body heuristic. This is a bounded error-page check, not general file-signature validation.
- **Soft error documents:** For nonmatching output types (including media, PDFs, archives and other direct files), an HTTP `200` labeled `text/html`, XHTML, JSON or problem+JSON is treated as an application failure, not as a completed download. The downloader library permits matching `.html`/`.htm`/`.xhtml` and `.json`/`.jsonl` files, but this does not expand the CLI directlink extractor’s supported URL extensions; problem+JSON is always rejected. A non-`200`/`206` status that escapes client redirect/error handling (such as `302` with redirects disabled or `202 Accepted`) is not proof of completed bytes. Actual `.html` downloads remain permitted. The conservative MIME check is not a complete content signature or malware detector; mislabeled error bodies can still require further validation.
- **Completed-media synchronization:** After the full response passes length/content checks, Galerith flushes and synchronizes the `.part` file with `sync_all()` before the completion rename can succeed. A write, flush or sync error is an unsuccessful download and cannot create an archive record; the incomplete part is retained for bounded recovery. This ensures the filesystem has acknowledged file data before successful completion, but it does not promise an atomic transaction across the rename, parent directory and separate SQLite archive database, nor immunity to damaged storage.
- **Atomic resume metadata:** For each fresh HTTP representation, Galerith removes the obsolete partial pair and writes the small validator sidecar through a separately created, synced `.part.json.tmp` file, then publishes it using a same-directory rename before starting the new partial. A crash while writing the temporary file therefore cannot leave a truncated canonical validator JSON. Stale temporary files are replaced without following temporary symlinks. This is targeted validator-file atomicity, not an end-to-end power-loss durability guarantee for the downloaded bytes or SQLite transactions.
- **Output and resume aliases:** Before deciding to skip an existing file or writing a partial, Galerith checks final/staging/sidecar filesystem entries and refuses existing symlinks and other nonregular entries. Unix staging files with multiple hard links are also rejected. This prevents ordinary stale/aliased outputs from being misclassified as downloaded media or truncating other files. Preflight checks and cooperative file locks do not provide a security guarantee against a hostile local process replacing paths concurrently.
- Successful overwrite downloads are recorded, but skipping an already existing filename does not imply download success by default. `--archive-event file` is the default and records completed downloads; `--archive-event skip` records only existing-file skips; `--archive-event file,skip` (or `skip,file`) records both. These are the pinned upstream `file` and `skip` archive-event subsets. The upstream `after` post-hook event is not implemented and is explicitly rejected.

**Limitations:** The native `downloads` table is Galerith-specific and is not gallery-dl's archive schema. Offline import covers only explicitly verified category and source-format subsets documented above, not arbitrary extractor IDs or custom archive-key templates. Native cache expiry, single-flight locking and recovery are implemented independently; this does not establish gallery-dl cache-schema parity. There is no general archive interchange, comprehensive source-metadata migration, or distributed cross-application reservation/claim protocol. File-output locks protect concurrent writes; archive locks additionally prevent cooperating Galerith processes from simultaneously downloading the same archive identity. gallery-dl and other writers do not honor these private locks.

## Offline migration acceptance evidence

[Full Linux CI 40226125555](https://github.com/sguzman/galerith/actions/runs/40226125555) verified the opt-in offline importer, repeated imports, exact SQLite byte preservation of the read-only source, rejection of missing references and URLs in import mode, safe quoted nondefault source tables, legacy archive behavior, and successful native lookups after removing the foreign archive. The isolated pinned gallery-dl oracle generated 13 real default directlink entry keys and checked their native import and source-free subsequent lookup. No unsupported extractor format is marked compatible.

The import is one native transaction. An invalid source value rolls back prior native inserts; the malformed-value rollback test passed [CI 40225614682](https://github.com/sguzman/galerith/actions/runs/40225614682). Signed URL credentials and original source paths are never stored in the imported-key table; only category names and SHA-256 digests are persisted. This does not provide general cache-expiry parity or complete gallery-dl archive interchange.

### Verified single-post archive IDs

The pinned Danbooru and E621 **direct-post** extractors use `{id}`, prefixed by their category for the implicit default table. Galerith now recognizes those keys only when the original input is a verified `danbooru.donmai.us/posts/ID`, `e621.net/posts/ID`, or `e6ai.net/posts/ID`, or `e926.net/posts/ID` source (including the pinned legacy post routes). New native records also preserve a category-scoped `direct-post-id:ID` so rotated CDN URLs can deduplicate a previously completed direct post. Older URL-hash records are promoted only after an exact matching download is established. Existing gallery-dl SQLite sources remain read-only and imported entries stay hashed.

This does **not** imply complete booru archive compatibility: only the verified direct-post, pool, Danbooru favorite-group, explicit-user e621-family favorite, scoped tag-search, Danbooru media-asset and explicitly dated daily/weekly/monthly popular formats documented below are supported. Implicit-current-date popular feeds, account-implicit favorites, unsupported source URLs and other upstream classes still lack fully verified archive IDs. The e926 category now matches upstream separately; earlier downloads recorded as `e621` can be recovered only from an **exact legacy media URL digest** on a verified e926 input. If that input has a supported scoped ID (including canonical tag searches), the exact-match recovery then promotes it to a stable source-scoped key; unsupported feeds remain URL-based. No unrelated e621/e926 archive histories are conflated. Named tables with bare IDs remain ambiguous without matching category-specific key prefixes.

### Source-scoped Danbooru/E621 pool archive IDs

Pinned upstream `DanbooruPoolExtractor` and inherited `E621PoolExtractor` both use `p_{pool[id]}_{id}`, **not** the direct-post `{id}` template. For confirmed Danbooru, e621, e926 and e6ai pool input URLs (`/pools/POOL` or `/pool/show/POOL`), Galerith composes an archive key from the pool ID and each returned post ID. Successful downloads additionally record native category-scoped `pool-id:POOL:post-id:POST` identities; same-pool CDN-token changes deduplicate, and all competing workers lock the same source-scoped key. Direct posts and other pools remain distinct even when their media belongs to the same post.

The offline importer recognizes only canonical, category-prefixed `CATEGORYp_POOL_POST` keys from the pinned upstream default table. For an explicitly named table, the actual keys must also carry the **same category prefix** configured by `--gallery-dl-archive-prefix CATEGORY`; a configured prefix affects how gallery-dl originally writes entries, not just how Galerith interprets them. Bare `p_POOL_POST` keys are always ignored as ambiguous across sites, even if a prefix is supplied during import. Only hashed imported keys enter the native database, and the foreign file stays read-only. Tag searches, favorites, popular feeds, media assets and other archive templates remain outside this limited pool compatibility scope.

### Danbooru favorite-group archive IDs

The pinned Danbooru favorite-group extractor has a distinct `fg_{favgroup[id]}_{id}` format. Galerith now recognizes that identity only for the already-supported canonical `danbooru.donmai.us/favorite_groups/GROUP` or `favorite_group/show/GROUP` routes. Both the source favorite-group ID and returned post ID determine the identity. Native records use category-scoped `favorite-group-id:GROUP:post-id:POST`; offline imports recognize the default `danboorufg_GROUP_POST` upstream key without writing plaintext source keys. Direct posts, tag searches and pools remain separate; unsupported variants and other sites are not generalized.

### Explicitly selected e621-family favorites

Pinned gallery-dl e621/e926/e6ai favorites use `f_{user_id}_{id}` (unlike direct posts, pools or Danbooru favorite groups). Galerith now accepts the subset with a **canonical explicit positive decimal** `user_id` in the original `/favorites?user_id=USER` URL. This identifies both the account and post without requiring credentials and remains stable across CDN URL changes. Duplicate `user_id` parameters, usernames/passwords in source URLs, missing IDs and noncanonical numeric IDs are excluded. A bare `/favorites` URL is intentionally still URL-hash-based because it relies on the active session and cannot safely identify the favorites owner.

Native records hold `favorite-user-id:USER:post-id:POST`, scoped by extractor category. External default `CATEGORYf_USER_POST` entries can be consulted read-only or imported into hashed native records. Named tables require their actual entries to carry the category-specific prefix explicitly configured for gallery-dl; bare `f_USER_POST` entries cannot be assigned to a site without proof. Tests cover cross-account isolation, per-site separation, idempotent privacy-preserving migration and lookups after deleting the upstream archive file.

### Source-scoped Danbooru and e621-family tag searches

Pinned Danbooru/E621 tag extractors use `t_{search_tags}_{id}`: the **complete decoded query string** and post ID are part of the archive key. Galerith now supports this for canonical Danbooru `/posts?tags=...` and e621/e926/e6ai `/posts?tags=...` or `/post?tags=...` URLs when they identify a unique `tags` parameter. Tags decoded from `+` and percent escapes are retained exactly for upstream lookup, while the new native identity stores only a SHA-256 digest of the category-prefixed archive key. No plaintext search terms, media URLs or signed tokens are written to the native archive. Distinct queries, direct posts, pools and account favorites cannot share source-scoped identities.

### Native public collection metadata cache (opt-in)

`--cache-db FILE` enables a **separate native SQLite cache** for already-supported, unauthenticated `https://danbooru.donmai.us/pools/ID.json`, `/favorite_groups/ID.json`, and `https://e621.net|e926.net|e6ai.net/pools/ID.json` metadata requests. Galerith's existing bounded JSON response reader remains authoritative; it caches only successful, byte-limited JSON for these strict first-party routes. It does not cache media bodies, arbitrary API calls, URLs with credentials/query parameters, or authenticated responses. `--cookies` conflicts with `--cache-db` to avoid cross-account caching.

Use `--cache-db ./metadata-cache.sqlite --cache-ttl 300` for a five-minute freshness window (300 seconds is the default). Allowed values are **0–86400 seconds**; explicitly selecting `--cache-ttl 0` disables expiry (`expires_at=0`, the pinned gallery-dl convention). Because pool metadata can change, indefinite caching is not the default. Expired records are re-fetched and stale rows are pruned on database reopen; intentional `expires_at=0` records survive pruning. Malformed or oversized records are discarded, and a failed refresh is never persisted. SHA-256 URL digests serve as cache keys, keeping source URL paths out of the cache index. Stable advisory files serialize concurrent refreshes across processes; SQLite commits provide atomic replacement, and OS process death releases held locks.

The format is **not** gallery-dl's Python-pickle cache and must not be opened or imported as that upstream database. The cache is an opt-in bounded preview, not full gallery-dl cache semantics or a substitute for its authentication-sensitive and per-extractor caches.

The shared extractor HTTP reader is tested with a deliberately unreachable local proxy: a scoped cached pool metadata response succeeds without network access, while an unscoped request cannot reuse it. Automatic HTTP redirects are checked against the originally requested endpoint, and redirected responses are **not** cached under a first-party metadata key. The cache's allowlist also rejects nonstandard HTTPS ports and credential-bearing URLs. Process-recovery tests terminate a separate worker after acquiring a cache lock and confirm that another process can use that key again without deleting lock files or losing SQLite integrity. These tests do not establish complete upstream cache interchange, per-extractor credentials or live-service parity. Downloads and existing archive identities remain separate from metadata cache entries.

### Cache file separation

The native collection cache must use a **different SQLite file** from both the native download archive and any read-only gallery-dl archive reference. Galerith rejects identical paths, symlinks, hard links and common relative-path aliases before opening or changing either database; the original reference bytes are preserved in the CLI regression. This is separate from the upstream Python-pickle cache format, which is never imported or overwritten by the native metadata cache.

### Interrupted and invalid-range transfer fixtures

Local HTTP integration tests exercise the real Galerith executable and archive database without external services. A 503 or truncated 200 response leaves no successful archive record. If a response with a validator leaves a partial file, Galerith resumes with `Range` and `If-Range`; only a complete, valid 206 response is promoted to the final media filename and recorded. A deliberately incorrect `Content-Range` is rejected, both partial file and validator sidecar are discarded, and no archive entry is made. A subsequent clean 200 fetch can complete and record exactly one successful item; a later invocation skips it from SQLite without another fetch.

These fixtures are focused evidence for failed transfers, validated resume and successful archive recording. They do not establish the full gallery-dl retry policy dialect across every extractor.

### Source-scoped archive safety and legacy migration

A completed download from a **verified extractor source** now writes exactly its category-scoped stable identity. It does **not** also write a global media URL fingerprint: the same unchanged CDN URL may legitimately appear in several distinct gallery-dl collections, searches, pools or upload-owner feeds, which must retain separate archive histories. For the same source identity, changed CDN URLs continue to deduplicate; an unrelated source must not inherit the recorded download even when its bytes or media URL match.

Earlier Galerith releases also stored an exact media URL fingerprint alongside stable source IDs. Because those historical fingerprints do not record *which source class* owned the media, they are ambiguous when a category has any source-scoped history. Galerith conservatively declines such URL-only promotion in mixed-history categories, preferring an extra download to a false archive skip; a purely URL-only legacy category can still promote an exact-match entry once to its verified stable source key. Tests cover identical media URLs across two feeds, same-file rotated media, historical mixed rows, and category-scoped migration safety. No old database or reference file is modified or deleted during this ambiguity check.
